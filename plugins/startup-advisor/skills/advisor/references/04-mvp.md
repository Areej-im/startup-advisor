## 1. Core idea

An MVP is a learning tool, not a smaller copy of the final product. Its purpose is to build the first version or experience that can test the critical hypothesis: can this solution deliver real value to real users? The shift in this stage is from learning through conversation and observation to learning through user behavior in front of a real experience, however limited.

## 2. What an MVP really is

- In Lean Startup, an MVP is the version that lets the team collect the maximum amount of validated learning about customers with the least reasonable effort. "Minimum" cannot be separated from "Viable": what is built must be enough for a meaningful test.
- An MVP is not necessarily a full app or platform, and not always a smaller or cheaper version of the final product (Blank). It can be a limited product, a manual service, a structured experiment, or a simple interface with manual work behind it.
- **The hypothesis decides the form**, not beauty or complexity:
  - Is the problem real? → problem interviews and observation may beat building.
  - Can the solution produce a better result? → an experience that actually delivers the result.
  - Will users pay? → a test close to a real payment decision; anything less is weak evidence.
- Before asking "what do we build?", ask "what is the biggest risk or most uncertain assumption we need to learn about now?"

## 3. Why not build the full product first

- Building everything first feels like control ("users will love it once it's complete") but may hide a big risk: lots of detail built on a wrong hypothesis.
- Every extra period of building before facing the market raises the cost of being wrong. More features don't fix a wrong customer, a mild problem, or a solution that doesn't fit the workflow — and they increase attachment, making change harder.
- Lean Startup's build–measure–learn loop: build only what lets you collect evidence for a decision. Shorter loops find mistakes earlier.
- Simplicity is not negligence. The first version can be narrow, but it must fit its test context and serve its few users seriously in the core task.

## 4. "Viable": minimum does not mean weak

- Minimum means removing what doesn't serve core learning — not removing value or credibility.
- If the version is so poor users can't reach the intended outcome, rejection doesn't show the problem is unimportant; the experiment may be invalid.
- "Enough" varies: consumer products — fast comprehension and ease of use; B2B — performing a defined part of the workflow; medical, financial, and other sensitive fields — safety, privacy, and compliance may set a higher bar before real users.
- Make the test small enough to reduce waste and serious enough to produce a meaningful signal.

## 5. Define the hypothesis the MVP tests

- "People will use our product" is too broad. Better: a specific user segment, with a specific problem, seeking a specific outcome, will accept a specific way of getting it, and will change behavior if the value is sufficient.
- Link every MVP to a **critical hypothesis** — one that, if wrong, changes the company's direction: problem severity, solution feasibility, willingness to pay, customer reachability, or usage frequency.
- Testing everything at once weakens learning: on failure, you can't tell whether it was the customer, design, pricing, channel, or execution. A focused test gives a clear result.
- Write before building: What do we believe? What is our current evidence? What do we want to learn? What behavior will we watch? What result will make us reconsider? This stops the team from reading every result in its favor.

## 6. From problem to the core of value

- The core of value is the part without which the product doesn't test its main promise: if it saves time on a recurring task, test that improvement; if it prevents a costly error, get close to that error; if it improves a decision, deliver an output that helps that decision.
- Teams start with long feature lists to look complete. Apparent completeness isn't needed early; reaching the value core is.
- Sort features into three groups:
  1. **Essential** to test the value
  2. **Supporting** — helps complete the experience without being its core (add only what safety and clarity need)
  3. **Deferrable** — doesn't affect the current hypothesis
- Every extra feature costs time, complexity, delay, and bugs. Cutting a feature can protect the quality of learning.

## 7. Talk to users before building

- Talk to suitable potential users so you don't build in isolation. One deep conversation can reveal a different problem framing, a stronger existing alternative, or that the user doesn't control the purchase.
- Focus on past behavior and real context, not future politeness. "When did this last happen?" beats "Would you use this?"
- Conversations shouldn't stop building forever; there's a moment to move from talk to test. But building with no user contact makes the MVP reflect the team's imagination.
- These conversations also find the first suitable users.

## 8. Fast launch ≠ random launch

- YC recommends moving fast to a testable first version. Useful speed is built on a specific user, a clear problem, limited scope, and a known learning question. Random launch puts the product in front of anyone and waits for vague signals.
- The first version can serve one customer type, one use case, or one workflow. Narrow scope ≠ small vision; it means a focused test.
- Treat launch as the start of a cycle, not a closing ceremony: watch behavior, talk to users, fix blockers, see whether the core value appears.

## 9. Short build-learn cycles

- Long development cycles delay facing reality. Break work into shorter learning units where possible.
- In each cycle define: the hypothesis tested, what will be built, the behavior or metric observed, and the decision the result supports.
- This resists feature creep: new ideas don't go straight onto the roadmap. Rank them by effect on the core hypothesis, ease of testing, and confidence in the need. Defer some, test some more simply, drop some.
- What matters is not coding speed alone but speed from assumption to evidence to decision.

## 10. Measurement before and after launch

- Decide before launch what you'll measure; metrics follow the hypothesis:
  - Recurring need → repeat use / retention matters more than signups.
  - Saves time → measure time or task completion.
  - Customer will pay → likes or clicks don't prove it.
- Prefer metrics that support a decision over numbers that look big. Total visits look good but don't show value; core-task completion, return, repetition, commitment, or payment are closer to the real question.
- Early data is thin. Combine qualitative observation with quantitative measures: How did they use it? Where did they get stuck? Did they return? What did they do unprompted? What patterns repeat?

## 11. User feedback after launch

- Before launch, ask about the problem and current behavior. After launch, ask about the actual experience: what they did, where they stopped, what was unclear, what was useful, what they ignored.
- Don't dismiss feedback because "it's only the first version" — key signals about core value and real blockers appear here.
- Don't implement every request literally. Users propose solutions based on tools they know; find the need or obstacle behind the request.
- Feedback is stronger tied to behavior: a feature request from a non-user differs from a recurring blocker reported by someone who relies on the product.

## 12. Concierge and Wizard of Oz MVPs

- You can test value without building a full system: deliver the service manually or do much of the work behind the scenes while the user gets the intended result.
- **Concierge MVP:** the experience is delivered manually and openly to a few customers, with close contact.
- **Wizard of Oz:** manual execution hidden behind an interface that looks automated. The two are not identical; don't use the terms interchangeably.
- Manual work reveals which steps repeat, where exceptions occur, what customers truly value, and what can be automated later.
- **Limits:** a manual test can show users want the result; it does not prove the system can produce it automatically, quickly, economically, or at scale. Be explicit about what was and wasn't tested.

## 13. Choosing the right test tool

| Tool | What it can test | What it cannot prove |
|---|---|---|
| Landing page | Message clarity, initial interest | Long-term use, payment |
| Clickable prototype | Comprehension, usability, flow | Real value delivered |
| Concierge / Wizard of Oz | Desire for the outcome; workflow learning | Automation, economics, scale |
| Working product | Real use, return, retention | Scalability of acquisition |

Not every test tool is automatically an MVP, and evidence strength differs. Pick the simplest tool that can reveal the needed truth, and interpret results within the limits of what was actually tested.

## 14. Choosing first users

- The best early users clearly live the problem, can try the solution in a real context, and will engage with an early version because the need matters to them.
- They're not the whole market; they're a first segment that helps you learn fast. The closer they are to the problem, the more relevant their behavior.
- Don't confuse friends with real users. Friends may be polite and may not have the problem. Use your network to reach users, but test with people who represent the target customer.
- The goal is real interaction showing whether value exists and where blockers are — not the biggest number.

## 15. What to leave out

- Scrutinize any feature that doesn't test the core hypothesis: advanced settings, broad customization, complex dashboards, many integrations, perfect design.
- Extra features can hide the truth: you can't tell which part created value or caused failure, and users may get stuck on complexity unrelated to the original problem.
- A small product that reveals the truth beats a large one that hides it.
- Keep a **"not now" list** as seriously as the "will do" list. It protects the team from chasing every new idea.

## 16. Testing is not a survey

- Many people say they'll use or pay, then behave differently at the real moment. Evidence is stronger with real behavior: time invested, data provided, repeated use, integration into workflow, financial commitment where appropriate.
- Interviews remain valuable for context and problem understanding. When testing the solution, look for signals closer to reality: Did they use it? Return? Ask for it again? Rely on it for a real task? Pay or take a serious step toward purchase?
- A survey tells you what people say about their intentions; a behavioral test tells you what they do in a near-real situation.

## 17. When an MVP succeeds

- Success doesn't mean ready to scale or that everything is proven. It means the MVP produced clear learning about an important hypothesis.
- Positive learning: use, return, commitment, willingness to pay. Negative but useful learning: wrong segment, problem not a priority, solution doesn't fit the workflow.
- The team should know more than before and connect the result to a decision. If you launched and can't say what you learned, the test wasn't designed clearly. Celebrating surface numbers without understanding behavior repeats the mistake next cycle.
- Define the success signal **before** the test, not after seeing results; it differs by product (return and repeat use vs. completing a critical task vs. an organization committing to a deeper trial).

## 18. Iterate or pivot

- No real usage or interest doesn't automatically mean the idea is dead: the problem may be the segment, message, access channel, experience quality, or the solution itself. Analyze before a big decision.
- **Iterate:** change something based on specific learning — clarify a step users repeatedly misunderstand; follow an unexpected part they use more than the core; investigate whether non-return means missing value or naturally infrequent use.
- **Pivot:** a bigger change makes sense when evidence accumulates that a core hypothesis doesn't hold, or a stronger opportunity appears elsewhere. It is a response to learning, not an escape from difficulty.
- Flexibility ≠ thrashing. Change what needs changing based on evidence, and stay clear about what was learned and why.

## 19. The founders' role

- This stage tests the founding team: what to cut, what to build, which user to focus on, which metric matters, when to iterate or pivot.
- Agree on the experiment's purpose. If one founder sees the MVP as a learning test and the other as a full official launch, tension follows over quality, scope, and time.
- Founders need direct proximity to users; much important knowledge never reaches summary reports.
- The MVP is not only a technical task; it is where product, customer, market, measurement, and learning meet.

## 20. MVP planning card

Help founders fill this in:

```
Critical hypothesis: [segment] with [problem] will [behavior] because [value].
Current evidence:     ...
What we want to learn: ...
Test form:            landing page / prototype / concierge / working product
Core features (only): ...
Not now:              ...
Behavior we'll watch: ...
Success signal (set before the test): ...
Result that makes us reconsider: ...
Time box:             ...
```

## 21. Diagnostic questions

- What is the one assumption that, if wrong, changes everything?
- What is the simplest thing that could test it in the next two weeks?
- Which features on your list are essential to test the value, and which are "not now"?
- Who are the first 5–10 users, and do they really live the problem?
- What behavior will tell you it worked? What would make you reconsider?
- Is your field sensitive (health, finance, security) and does it need a higher bar before real users?

## 22. Common mistakes

| Mistake | How to respond |
|---|---|
| Building the whole vision into v1 | Find the critical hypothesis; cut to the value core. |
| "Minimum" so weak users can't reach the outcome | A failed test of a broken experience proves nothing. |
| Testing everything at once | One focused hypothesis per test. |
| Treating landing-page signups as proof of demand | It tests the message, not use or payment. |
| Treating a concierge success as proof of scale | It tests desire for the outcome, not automation or economics. |
| Defining success after seeing results | Write the success signal before launching. |
| Implementing every user request literally | Find the need behind the request. |
